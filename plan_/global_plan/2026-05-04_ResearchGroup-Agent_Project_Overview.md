# ResearchGroup-Agent 项目整体大纲

## 1. 项目定位

ResearchGroup-Agent 是一个面向科研课题组场景的多 Agent 协作系统。

系统目标是模拟一个真实研究生课题组的运行方式：由导师 Agent 负责整体规划、任务拆解和成果审核；多个研究生 Agent 根据不同能力画像分工协作；必要时研究生 Agent 可以创建临时本科生 SubAgent 完成短期子任务；系统负责记录任务状态、协作过程、阶段性产出，并提供可视化管理能力。

一句话概括：

> 用多 Agent 模拟一个导师带多个研究生完成科研任务的全过程。

---

## 2. 项目要解决的问题

当前科研项目协作中常见问题包括：

- 导师难以及时掌握每个学生的任务进度；
- 学生之间分工不清，协作过程不透明；
- 文献调研、工程实现、实验执行、数据分析、报告写作等环节割裂；
- 阶段性成果难以沉淀；
- 多人协作产生大量上下文，容易混乱；
- 缺少一个可以展示“谁在做什么、进展如何、产出是什么”的统一系统。

ResearchGroup-Agent 的目标是通过多 Agent 组织结构和任务板机制，把科研协作过程结构化、可追踪、可复盘、可产出。

---

## 3. 系统核心角色

### 3.1 导师 Agent

导师 Agent 是系统最高决策者，负责：

- 接收用户输入的研究目标；
- 拆解任务；
- 分配任务；
- 监控进度；
- 审核结果；
- 要求返工；
- 汇总阶段性成果。

### 3.2 研究生 Agent

第一版设置五类研究生 Agent：

| Agent 类型 | 主要职责 |
|---|---|
| 调研型研究生 Agent | 文献检索、论文总结、相关工作梳理 |
| 工程型研究生 Agent | 代码实现、系统架构、接口开发 |
| 实验型研究生 Agent | 实验设计、实验执行、参数记录 |
| 数据分析型研究生 Agent | 数据清洗、指标分析、结果解释 |
| 写作型研究生 Agent | 周报、报告、论文草稿、总结材料 |

研究生 Agent 不是固定工具人，每个 Agent 都有多个能力维度，只是主攻方向不同。

### 3.3 本科生 SubAgent

本科生 SubAgent 是研究生 Agent 临时创建的轻量级子 Agent。

特点：

- 临时存在；
- 会话隔离；
- 只接收最小必要上下文；
- 完成明确子任务；
- 返回结构化结果；
- 返回后销毁。

SubAgent 主要用于处理短周期、低风险、输入输出明确的辅助任务。

## 4. 系统核心机制

### 4.1 能力画像机制

每个研究生 Agent 都有能力分数，用于任务分配和协作调度。

推荐能力维度：

- 文献调研；
- 工程编码；
- 实验执行；
- 数据分析；
- 学术写作；
- 指导管理。

能力评分不是评价真实能力，而是系统调度参数。

### 4.2 任务需求画像机制

每个任务也有能力需求，用于匹配合适的主责 Agent 和协作 Agent。

任务可以包含：

- 任务类型；
- 优先级；
- 复杂度；
- 可拆分性；
- 所需能力；
- 主责 Agent；
- 协作 Agent；
- 产出要求。

### 4.3 主责 Agent 与协作 Agent 机制

每个任务应有一个主责 Agent，对最终结果负责。

其他研究生 Agent 可以作为协作 Agent 参与部分任务，例如：

- 工程型 Agent 协助调研型 Agent 分析 GitHub 项目；
- 数据分析型 Agent 协助实验型 Agent 解释实验结果；
- 写作型 Agent 协助其他 Agent 整理最终报告。

### 4.4 空闲 Agent 支援机制

当某个 Agent 负载较高，而其他 Agent 空闲时，系统可以安排空闲 Agent 支援任务。

支援不要求完全专精，只要相关能力达到一定水平即可。

### 4.5 SubAgent 委派机制

研究生 Agent 可以将明确、短期、低上下文依赖的任务委派给本科生 SubAgent。

SubAgent 的结果不能直接进入最终产出，必须由研究生 Agent 检查、筛选和整合。

## 5. 系统主要模块

### 5.1 用户输入模块

用于输入研究目标、项目主题、任务需求或阶段性目标。

### 5.2 导师 Agent 模块

负责理解目标、拆解任务、分配任务、审核结果和生成总结。

### 5.3 研究生 Agent 模块

负责执行具体任务，并在必要时请求协作或创建 SubAgent。

### 5.4 SubAgent 模块

负责完成临时子任务，并返回结构化结果。

### 5.5 任务调度模块

负责根据能力画像、任务需求、当前负载和任务状态进行分配与调度。

### 5.6 任务板模块

用于展示和管理任务状态，包括：

- 待分配；
- 已分配；
- 执行中；
- 等待协作；
- 等待 SubAgent 返回；
- 等待导师审核；
- 需要返工；
- 已完成；
- 已归档。

### 5.7 可视化模块

可视化是系统级功能，不单独设置可视化 Agent。

主要展示：

- 当前任务列表；
- Agent 当前状态；
- Agent 负载；
- 协作关系；
- SubAgent 调用记录；
- 阶段性产出；
- 项目进度时间线。

### 5.8 产出管理模块

用于管理系统生成的阶段性成果，例如：

- 任务拆解表；
- 文献调研总结；
- 实验计划；
- 数据分析结论；
- 周报；
- 技术报告；
- 项目总结。

## 6. MVP 阶段目标

MVP 阶段目标不是做完整科研自动化，而是跑通一个可演示的课题组协作闭环。

核心流程：

```text
用户输入研究目标
→ 导师 Agent 拆解任务
→ 系统分配给五类研究生 Agent
→ 研究生 Agent 执行任务
→ 必要时研究生之间协作
→ 必要时创建本科生 SubAgent
→ 任务板更新状态
→ 导师 Agent 审核结果
→ 生成阶段性产出
```

MVP 应重点展示：

- 多 Agent 组织结构；
- 能力画像；
- 任务分配；
- 协作执行；
- SubAgent 临时委派；
- 状态追踪；
- 阶段性产出。

---

## 7. MVP 阶段不做的事情

为了控制范围，MVP 阶段暂不做以下内容：

- 不做真实论文自动发表；
- 不做复杂深度学习实验平台；
- 不做真实多人账号权限系统；
- 不做复杂组织架构；
- 不做能力分数自动学习；
- 不做无限层级 SubAgent；
- 不做真实导师/学生替代；
- 不做完整科研知识库；
- 不做过度拟人化角色设定。

MVP 的重点是系统闭环，而不是追求完整科研能力。

## 8. 后续扩展方向

后续可以逐步扩展：

- 接入真实文献检索工具；
- 接入 GitHub；
- 接入代码执行环境；
- 接入实验日志系统；
- 接入数据库和文件系统；
- 支持多个课题组；
- 支持多个导师 Agent；
- 支持更复杂的 SubAgent 管理；
- 支持导师反馈驱动的能力分数调整；
- 支持长期记忆和项目知识库；
- 支持真实科研产出归档。

---

## 9. 项目核心亮点

ResearchGroup-Agent 的核心亮点包括：

1. 不是单个科研助手，而是虚拟课题组；
2. 导师 Agent 统一规划、分配和审核；
3. 研究生 Agent 有能力画像，不是固定工具人；
4. 研究生之间可以横向协作；
5. 研究生可以纵向委派本科生 SubAgent；
6. SubAgent 会话隔离，用完即销毁，避免上下文污染；
7. 系统提供任务板和状态可视化；
8. 系统最终沉淀阶段性科研产出。

---

## 10. 项目一句话说明

ResearchGroup-Agent 是一个模拟真实科研课题组运行方式的多 Agent 协作系统：导师 Agent 负责规划和审核，研究生 Agent 按能力画像分工协作，本科生 SubAgent 执行临时子任务，系统负责调度、追踪、可视化和阶段性产出沉淀。
