# ResearchGroup-Agent 深度分析与升级计划

**日期：** 2026-06-01  
**分析版本：** v2.0 (基于 main 分支 545d650)  
**核心问题：** 文献调研Agent持续产生假文献/不相关文献，导致任务反复被打回，网络搜索未能纠正

---

## 一、问题诊断：为什么调研Agent总产出假文献

### 1.1 根本原因链

```
用户研究目标（复杂/专业）
    ↓
query生成过于粗暴（直接拼接title+description）
    ↓
学术API返回结果与目标不匹配
    ↓
LLM在"归纳"阶段补充了记忆中的假文献
    ↓
学术诚信检测未能有效拦截（白名单基于同批搜索结果）
    ↓
导师审核打回 → 返工 → 同样的query → 同样的结果
    ↓
死循环（最多2轮后强制结束，质量不达标）
```

### 1.2 六大具体问题

#### 问题①：Query构建无智能改写

**现状**：`evidence_pipeline_service._query_for_task()` 直接拼接 `description + title` 作为搜索字符串。

```python
# 当前实现 (evidence_pipeline_service.py)
return " ".join([
    primary_goal(str(root_task.get("description") or "")),
    str(root_task.get("title") or ""),
]).strip()
```

**后果**：
- 用户写"研究多Agent协作在科研场景的应用"，query就是整句话
- CrossRef/OpenAlex对自然语言长句搜索效果极差，它们设计用于关键词/短语搜索
- 搜索结果往往是泛泛相关的论文，而非精确匹配研究目标

#### 问题②：LLM幻觉未被有效遏制

**现状**：虽然有"学术诚信注入"的prompt指令，但LLM生成时的核心矛盾是：

1. Prompt要求Agent"归纳和总结"搜索到的文献
2. 搜索结果可能只有3-5篇泛泛相关的论文
3. LLM为了满足"充分覆盖"的评审标准，倾向于从训练数据中补充论文
4. `allowed_sources` 白名单是基于**当次搜索结果**构建的，如果LLM在JSON输出中编造了一个看起来合理的source_id，白名单检查可能被绕过

**关键代码路径**（`task_executor.py`中文献任务的执行）：
```
搜索 → 得到allowed_sources → 注入prompt → LLM生成 → 检查references_used是否在allowed_sources中
```

问题在于：LLM可能不在`references_used`字段里放假文献，而是在正文的`findings`/`summary`中直接描述假论文内容，引用检查只查JSON的`references_used`字段。

#### 问题③：搜索-归纳的架构断裂

**现状**：搜索和LLM生成是两个独立步骤，中间缺乏迭代：

```
搜索（一次性）→ 结果注入prompt → LLM一次性生成最终输出
```

**缺失**：
- 没有"搜索→初步判断→补充搜索→深入阅读"的多轮迭代
- 没有基于初次搜索结果的query refinement
- 没有让LLM判断"当前证据是否足够回答问题"的中间步骤

#### 问题④：返工机制无法根本改善

**现状**：导师打回后创建修订任务，但：
- 修订任务使用的query来源于`revision_of_task_id`追溯到原始任务
- 原始任务的description/title没变 → **query不变** → **搜索结果不变**
- LLM只是被告知"上次被打回了，请改进"，但没有新的证据输入
- 结果：要么重复之前的错误，要么编造新的假文献来"满足要求"

#### 问题⑤：Tavily网络搜索默认关闭

**现状配置**：
```
WEB_SEARCH_ENABLED=false      # 默认关闭！
TAVILY_API_KEY=               # 空
BROWSER_RESEARCH_ENABLED=false # 默认关闭！
```

用户可能以为"接入了网络搜索"，实际上只有CrossRef/OpenAlex/arXiv三个学术API在工作。这三个API：
- CrossRef：按关键词匹配论文元数据，对中文query几乎无效
- OpenAlex：覆盖面广但排序算法对精确topic匹配不友好
- arXiv：只覆盖预印本，很多领域论文不在arXiv上

#### 问题⑥：Fallback到硬编码文献库

`literature_source_service.py` 中的 `TRACEABLE_LIBRARY` 只包含7篇固定论文（GPT-4, Claude, LLaMA, Gemini等大模型相关）。当远程搜索无结果时回退到这些论文，导致：
- 无论用户研究什么主题，fallback文献都是大模型基础论文
- 这些文献与用户实际研究目标严重不符

## 二、系统性架构缺陷分析

### 2.1 "玩具项目"的核心表现

| 维度 | 当前状态 | 真正可用的研究系统应有 |
|------|----------|----------------------|
| 文献搜索 | 一次性搜索，query=原文 | 多轮迭代搜索，query改写，相关性排序 |
| 证据验证 | 白名单字段检查 | 全文对比，DOI解析验证，引用图谱交叉验证 |
| LLM控制 | prompt指令"不要编造" | 强制grounding（只能引用提供的文本片段） |
| 错误恢复 | 同样的query重试2次 | 根据失败原因调整策略，扩大/缩小搜索范围 |
| 知识积累 | 每次run独立 | 跨run的文献库、已验证来源缓存 |
| 人机协作 | HITL只在关键节点 | 用户可随时介入修正方向、提供种子论文 |
| 搜索覆盖 | 英文学术API为主 | 多语言、多数据库、Google Scholar、DBLP等 |

### 2.2 Agent架构根本性问题

当前架构是 **"先搜后生"的单程管道**：

```
[搜索] ──→ [LLM生成] ──→ [检查] ──→ 通过/打回
```

真正有效的研究Agent应该是 **"搜索-思考-搜索-验证"的循环体**：

```
[思考：需要什么信息] ──→ [搜索策略制定] ──→ [执行搜索]
        ↑                                        ↓
[综合判断：够不够]  ←──── [评估结果相关性] ←──── [初步过滤]
        ↓
[不够] → [调整策略，补充搜索]
[够了] → [基于已验证来源归纳]
```

### 3.3 Phase 2：重构搜索架构

#### 2A. 引入ReAct式迭代搜索

**核心思想**：让调研Agent具备"思考-行动-观察"的循环能力。

```python
class IterativeResearchAgent:
    """
    替代当前的一次性搜索+LLM生成模式
    """
    
    async def research(self, goal: str, max_iterations: int = 5) -> ResearchResult:
        knowledge_base = []  # 已验证的知识
        search_history = []  # 避免重复搜索
        
        for i in range(max_iterations):
            # Step 1: 思考 - 当前知识够不够？还缺什么？
            analysis = await self.llm.generate(
                prompt=self._think_prompt(goal, knowledge_base, search_history),
                schema=ThinkingSchema  # {sufficient: bool, gaps: list, next_queries: list}
            )
            
            if analysis.sufficient:
                break
            
            # Step 2: 行动 - 执行新搜索
            for query in analysis.next_queries:
                results = await self.search_all_sources(query)
                search_history.append(query)
                
                # Step 3: 观察 - 评估结果相关性
                relevant = await self.filter_relevant(results, goal)
                verified = await self.verify_sources(relevant)
                knowledge_base.extend(verified)
        
        # 最终归纳（严格基于knowledge_base）
        return await self.synthesize(goal, knowledge_base)
```

```python
class RelevanceRanker:
    """
    对搜索结果进行相关性排序，避免把不相关论文喂给LLM
    """
    async def rank(self, results: list[Paper], goal: str) -> list[ScoredPaper]:
        # 方法1: 基于embedding的语义相似度
        goal_embedding = await self.embed(goal)
        for paper in results:
            paper_embedding = await self.embed(paper.title + " " + paper.abstract)
            paper.relevance_score = cosine_similarity(goal_embedding, paper_embedding)
        
        # 方法2: LLM判断相关性（更准确但更贵）
        # 方法3: 混合排序（BM25 + 语义）
        
        return sorted(results, key=lambda p: p.relevance_score, reverse=True)
```

### 3.5 Phase 4：知识积累体系

#### 4A. 跨Run文献缓存

```python
class LiteratureCache:
    """
    已验证文献的持久化缓存，避免重复搜索和验证
    """
    
    async def get_or_search(self, query: str) -> list[Paper]:
        # 1. 先查缓存（相似query的历史结果）
        cached = await self.find_similar(query, threshold=0.85)
        if cached:
            return cached
        # 2. 缓存miss时执行新搜索
        results = await self.evidence_provider.search(query)
        # 3. 验证后存入缓存
        verified = await self.verify(results)
        await self.store(query, verified)
        return verified
```

#### 4B. 用户种子文献机制

```python
class UserSeedLiterature:
    """
    允许用户在创建研究任务时提供种子论文
    """
    
    # 用户可以：
    # 1. 提供已知论文的DOI/URL/标题
    # 2. 上传PDF文件提取引用列表
    # 3. 指定关键作者/会议/期刊
    # 4. 这些种子信息用于引导搜索方向
    
    async def expand_from_seeds(self, seeds: list[Paper]) -> list[Paper]:
        """从种子论文的引用列表出发，滚雪球式扩展"""
        expanded = []
        for seed in seeds:
            # 获取引用该论文的论文（forward citation）
            citing = await self.get_citing_papers(seed.doi)
            # 获取该论文引用的论文（backward citation）
            cited = await self.get_references(seed.doi)
            expanded.extend(citing + cited)
        return expanded
```

## 六、总结

当前项目 **架构设计是合理的**（三层验证、多源搜索、学术诚信检测），但存在以下致命短板：

1. **搜索query质量差** → 搜不到相关论文 → LLM被迫编造
2. **默认配置保守** → 最强的搜索能力（Tavily+浏览器）全部关闭
3. **单程管道无迭代** → 一次搜索不够就没有第二次机会
4. **返工机制形同虚设** → 同样的query搜同样的结果
5. **Grounding不够严格** → LLM可以在正文中混入未验证内容

解决核心矛盾的关键是：**从"一次搜索+一次生成"变为"多轮搜索+逐步验证+严格grounding"**。这不仅是代码改动，更是Agent设计范式的转变——从"让LLM直接产出最终结果"变为"让LLM成为搜索策略的决策者，让搜索结果成为唯一的知识来源"。
