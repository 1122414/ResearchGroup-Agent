## 2. 技术可行性分析

### 2.1 技术栈评估

| 技术选择 | 可行性 | 风险点 | 缓解措施 |
|----------|--------|--------|----------|
| Python FastAPI 后端 | ✅ 高 | 无 | 成熟技术，文档齐全 |
| SQLite 数据库 | ✅ 高 | 并发写有限 | MVP 单用户，无影响 |
| Pydantic 数据模型 | ✅ 高 | 与 FastAPI 深度集成 | 标准选择 |
| React/Next.js 前端 | ✅ 高 | 需要前端开发能力 | 页面简单，5 页 |
| Tailwind CSS | ✅ 高 | 无 | 可选 shadcn/ui 加速 |
| 自研轻量调度器 | ⚠️ 中 | 调度规则复杂性 | 规则已明确量化，可算法化 |
| MockLLMProvider | ✅ 高 | mock 结果逼真度 | 固定模板保证演示稳定性 |
| LLMProvider 抽象 | ✅ 高 | 无 | 简单 Strategy 模式 |

### 2.2 核心难点分析

#### 难点 1：导师 Agent 任务拆解的稳定性

- **问题**：LLM 拆解任务时可能输出不符合 JSON Schema 的结果
- **影响**：整个流程依赖拆解结果，拆解失败则后续全部阻塞
- **评估**：⚠️ 中风险
- **缓解**：
  - Mock 模式使用固定模板，稳定可靠
  - 真实 LLM 模式需要 Output Parser + 重试机制
  - 建议 P0 阶段优先确保 Mock 模式跑通，再接入真实 LLM

#### 难点 2：SubAgent 上下文隔离

- **问题**：如何确保 SubAgent 只收到"最小必要上下文"
- **影响**：上下文泄露会导致 SubAgent 越权或产生幻觉
- **评估**：⚠️ 中风险
- **缓解**：
  - MVP 阶段 SubAgent 是轻量级任务，可通过 Prompt Engineering 约束
  - 每个 SubAgent 创建时显式构造 isolated prompt
  - 结构化的 output_schema 保证返回格式可控

#### 难点 3：调度公式的实际效果

- **问题**：`能力匹配分 * 0.7 + 空闲程度 * 100 * 0.3` 公式中量纲不一致
- **影响**：空闲程度乘以 100 会导致该维度权重过高
- **评估**：⚠️ 低风险（MVP 阶段可调参）
- **建议**：实际实现时考虑归一化处理，或降低空闲权重系数的引入方式

#### 难点 4：前端与后端的状态同步

- **问题**：step 模式下前端需要实时反映后端状态变化
- **影响**：无 WebSocket 情况下，轮询可能延迟
- **评估**：⚠️ 低风险
- **缓解**：MVP 使用 HTTP 轮询即可，不需要 WebSocket

### 2.3 数据模型可行性

- **Agent 模型**：6 维度能力分数 + 状态枚举 + 负载字段 → 简单清晰
- **Task 模型**：required_skills + status 枚举 + owner/collaborator → 支持所有调度需求
- **SubAgent 模型**：parent_agent + task_id + lifecycle → 可完整追踪
- **状态枚举**：TaskStatus（10 状态）、AgentStatus（6 状态）→ 覆盖所有阶段

**结论**：数据模型设计充分，无需额外表/字段即可支撑 MVP 全部功能。

### 4.2 项目风险

| 风险 | 概率 | 影响 | 等级 | 缓解措施 |
|------|------|------|------|----------|
| 需求蔓延 | 中 | 高 | 🔴 | 严格执行第 3 节"严禁做"清单 |

**建议**：P0 阶段 Mock 优先。P2 接入真实 LLM 时，为导师 Agent 的 task decomposition 添加输出格式校验 + 自动重试 + 降级到模板的逻辑。

## 5. 架构评审

### 5.1 优点

1. **分层清晰**：api → services → models → storage，标准 FastAPI 分层
2. **接口预留充分**：ToolProvider、AgentOrchestrator、SkillUpdateService、ExternalMemory 均预留
3. **Prompt 分离**：所有 prompt 独立为 .md 文件，不硬编码到代码中
4. **Mock 优先**：保证无外部依赖时的可用性和演示稳定性
5. **目录结构规范**：前后端分离，artifacts 独立存储

### 5.2 潜在改进点

1. **调度器单点**：当前 TaskScheduler 承担了分配、负载计算、协作选择多重职责，建议按职责拆为 `TaskAssigner` + `LoadBalancer` + `CollabSelector`
2. **状态机显式化**：当前 TaskStatus 流转是隐式的，建议在 Task 模型上添加 `allowed_transitions` 约束
3. **Run 模型隔离**：已设计了 Run 模型，但 Task 与 Run 的关联未在数据模型中明确体现
4. **错误处理**：计划中未提及 Agent 执行失败、SubAgent 超时等异常路径的 fallback 策略

### 5.3 架构演进路径

```
MVP (自研调度器)
  → P2 (接入真实 LLM)
    → 后续 (LangGraph/AutoGen 替换 AgentOrchestrator)
      → 后续 (向量数据库接入 ExternalMemory)
        → 后续 (真实工具接入 ToolProvider)
```

此演进路径在 Global Plan 中有明确规划，MVP Plan 预留了所有接口，架构上可平滑升级。

## 9. 附：关键公式验证

### 9.1 主责 Agent 匹配分

以"文献调研任务"（literature_survey）为例，验证分配是否正确：

```
调研型研究生匹配分（能力匹配分 * 0.7 + 空闲程度 * 100 * 0.3）：
  能力匹配分 = 10*9 + 4*2 + 5*1 + 6*4 + 8*7 + 8*6 = 90 + 8 + 5 + 24 + 56 + 48 = 231
  空闲程度 = 1.0（首次分配）
  最终分 = 231 * 0.7 + 1.0 * 100 * 0.3 = 161.7 + 30 = 191.7

工程型研究生匹配分：
  能力匹配分 = 4*9 + 10*2 + 7*1 + 6*4 + 5*7 + 7*6 = 36 + 20 + 7 + 24 + 35 + 42 = 164
  空闲程度 = 1.0
  最终分 = 164 * 0.7 + 30 = 114.8 + 30 = 144.8

结果：调研型 191.7 > 工程型 144.8 ✅ 分配正确
```

### 9.2 调度公式潜在问题

如前所述，`空闲程度 * 100 * 0.3` 的最大贡献为 30，而能力匹配分的范围约为 50-250，乘以 0.7 后为 35-175。这意味着空闲程度在分数中的占比约为 15-37%，量纲问题影响可控，但不够优雅。建议实现时做归一化处理。
